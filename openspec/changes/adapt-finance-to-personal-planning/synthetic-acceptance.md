# Synthetic conversational acceptance

This is an implementation review and reusable synthetic walkthrough for task 8.2. Its prompts, accepted facts and source rows are fixtures. It is not a transcript of a live user's financial activity, a Google provider login, a hosted plugin deployment or a claim that every external model follows the guidance. The actual protocol/integration results and remaining limitations are recorded separately in the change's verification record.

## Shared fixture and acceptance rules

Use a disposable local workspace with an accepted time zone, an authorized MXN book and reviewed cash/bank, investment, loan and credit-card accounts. Names such as `Mi coche` and `Hamburguesa` are preserved user data. MXN is an explicitly accepted fixture choice; Spanish, Mexico City, a currency symbol or the word pesos does not establish it.

Inspect `get_session` and authorized context before setup. Reuse accepted choices and continue bounded pages before treating one result as unique. Existing onboarding retains its reviewed names, city-based zone help and one complete setup review; selecting a suggested name alone creates nothing. Finance reads require the independent book grant. All writes and recovery require a current writer, session and consent, with explicit accepted self or null attribution.

Amounts are exact strings. Dates are real concrete calendar dates or explicit month periods. Reliable message-time context can suggest a date in the workspace zone; otherwise disclose the server's current local date and obtain acceptance of that proposed assumption. Freeze accepted values, resource identifiers and the request UUID across uncertain retries. Complete accepted supported instructions proceed without a redundant confirmation. Tool metadata guides this conversation; strict contracts and transactional authorization enforce the backend boundary.

## Walkthrough cases

| Case and synthetic user intent | Focused conversation and accepted interpretation | Expected supported action and evidence |
| --- | --- | --- |
| Salary received: the user supplies `500.00` MXN, a reviewed bank account, concrete date and accepted attribution. | Keep the user's description. No additional question is needed when all values are accepted. Distinguish salary actually received from a future salary estimate. | `record_transaction` single `income` with a destination only. Cash flow includes one income; a future salary instead becomes an expected income line through `manage_plan`. |
| Hamburger: `Compré una hamburguesa`. | Retain the description and ask only missing amount, currency, account, date or attribution. Reuse accepted context and offer help when context is absent. Do not assign a category or choose MXN from language. | Once resolved, submit one expense using the supported exact contract. Onboarding alone never claims the hamburger was recorded. The unchanged `record_expense` path remains compatible with old clients. |
| Card purchase followed by paying the card. | Establish the reviewed credit-card and paying bank accounts. Explain that the accepted purchase and later repayment have separate meanings. | Purchase: expense from the card. Payment: transfer from bank to card. The purchase contributes once to spending; repayment does not become another purchase expense. This records evidence and does not execute a bank payment. |
| Loan proceeds and an installment with an unknown split. | Loan proceeds require an accepted liability-to-bank transfer. Ask for known principal, interest and fee facts for repayment. Preserve missing terms as unknown. | Proceeds are a transfer, not earned income. An accepted `2400.00` expected installment without components remains an unresolved plan with that quoted total and no invented typed lines. Known principal/interest/fee components can later resolve the quote exactly and post as one atomic accepted group. No amortization or payoff date is invented. |
| Contribution to CETES already represented by an investment account. | Reuse that account. If its type/opening date is unknown, propose the explicit review without changing the opening amount. Identify whether the holding is already represented before considering a manual asset. | Owned bank-to-investment movement is a transfer, not an expense, income or second asset. An applicable accepted valuation changes the report value of that investment once and leaves its ledger untouched. |
| Recurring day-31 bill. | Obtain monthly or annual interval, start/end periods, exact component values and the optional due day. Ask for `last_day` versus clarification/rejection when a short month has no day 31. A month-only commitment retains a null due date. | `manage_plan` creates a rule and materializes a bounded accepted horizon of at most 100 occurrences. February 2028 uses the accepted last-day policy and resolves to February 29. Repeating the same action or using a fresh key for an existing occurrence creates no duplicate. Rule changes preserve settled history. |
| A bill partially paid, or principal overpaid while interest remains unpaid. | Request an actual matching movement, not just a paid label or coincidentally equal text. Keep kind, account and category compatibility. Explain unallocated or excess evidence separately. | Link accepted components without making another actual movement. A `600.00` allocation to a `1000.00` component leaves `400.00` due. Excess on one component does not settle another incompatible component. Revocation and correction retain allocation identifiers/history and require explicit reconciliation. |
| Workbook row contains only a monthly actual amount. | Review source selection, role, exact parsing rule, currency and category. Do not ask the user to invent a day or bank account just to fit a daily transaction. A future-year tab is a clue requiring review, not proof that all its rows are planned. | Preview a frozen `actual_summary` row, then commit only an accepted ready batch. Store a monthly summary and reviewed coverage, without fictional day, transaction, person or account effect. A monthly plan instead retains month precision. |
| Dashboard and monthly components conflict. | Present the observed `202338.51` headline, `95511.47` monthly sum and `106827.04` difference as source reconciliation evidence. Ask which active ranges/rows, adjustments and actual-versus-planned periods are authoritative. Exclude derived Dashboard totals and hidden backup/archive candidates only through accepted selection. | Preview retains blockers until the bounded batch's source/mapping/coverage and reconciliation are self-contained and accepted. Neither source total is declared verified savings, formulas are not repaired, and a preview is not reported as an import. |
| Cancel before submission, cancel a committed expectation, or cancel a goal. | A pre-submission cancellation ends without a tool write. For committed records, identify the exact plan/rule/goal and current version. Explain previously committed outcomes precisely. | Explicit plan/rule cancellation preserves actual payments and settled history. Goal cancellation preserves account money and allocation history. Neither action erases posted movements. A transaction void is a separate controlled correction with reason and allocation reconciliation. |
| An expense response times out or a multi-step setup partially succeeds. | Keep the original request UUID, payload and concrete date for that uncertain action. Retain completed book/account IDs. If account creation succeeded but configuration failed, report the existing unknown-type account and retry only the unresolved configuration. | Identical authorized recovery returns the original identifiers with `already_processed`; changed payloads conflict, retired actions are not recreated and revoked writers cannot recover through an old receipt. A fresh key must not be used to guess whether an uncertain expense committed. Separate import batches report committed, blocked and pending progress truthfully. |
| Savings goal or manually tracked asset. | A target for a desired car is a goal; it does not prove an owned car exists. An owned holding requires accepted identity/ownership and a reviewed choice that it is distinct from ledger holdings. Use accepted backing and freshness assumptions for earmarks. | Goals reserve eligible supported funds without changing balances. Concurrent goals cannot allocate the same available money twice. Later spending or stale/changed valuation backing discloses a shortfall. Asset values use exactly one target, explicit date/source and preserved correction history; zero remains distinct from unknown. |
