# Database catalogue

This catalogue describes the existing declarative model: six application schemas, 40 tables (including 23 Finance tables), and four private Auth projection views. Exact columns, defaults, constraints, indexes, RLS, and privileges live in the linked [canonical SQL tree](../../apps/supabase/schemas/); reviewed upgrades live in [migrations](../../apps/supabase/migrations/). PostgreSQL 17 is configured in [config.toml](../../apps/supabase/config.toml).

The [database-model specification](../specs/database-model/spec.md) defines the current boundary. The preserved [original data model](original-data-model.md) contains design provenance and proposed operations as well as implemented structure; it is not proof that every described service exists.

## Current application scope

The [personal-planning change](../changes/adapt-finance-to-personal-planning/proposal.md) extends the compatible six-tool Finance foundation with typed accounts, categories, general recording and corrections, plans and settlements, debt terms, goals, valuations, reports, and reviewed import. Its [verification record](../changes/adapt-finance-to-personal-planning/verification.md) records the completed native, unit/protocol and integrated local checks. The [MCP source](../../apps/supabase/functions/impulso-api/mcp.ts) and runtime remain the canonical tool surface; schema existence alone never exposes a tool. Hosted API version 3 now exposes the same 20 tools, and all ten migrations are applied remotely. The [rollout verification](../guides/remote-deployment.md#finance-rollout-verification) records 40 RLS-enabled application tables, refreshed plugin discovery and an authenticated session check without creating salary, financial records or live workbook imports.

Onboarding writes six Core tables. The local and hosted Finance services use [the original expense path](../../apps/supabase/functions/_shared/finance.ts), [ledger services](../../apps/supabase/functions/_shared/ledger.ts), [planning/debt/wealth services](../../apps/supabase/functions/_shared/planning.ts), [report services](../../apps/supabase/functions/_shared/reports.ts), and [reviewed import services](../../apps/supabase/functions/_shared/finance_imports.ts) with [strict contracts](../../apps/supabase/functions/_shared/import_contracts.ts). New mutations retain transactional authorization, redacted book-linked audit, and actor-bound receipts. Legacy account and expense contracts and version-one fingerprints remain unchanged.

Attribution remains the actor's verified active self with basic-person access, or explicitly accepted unassigned null. Membership and basic-person permission do not replace a current book grant. Managed people, sharing, ownership transfer, Health, file services, bank execution, FX, automatic amortization/pricing, and purge execution remain unsupported. Applying this change imports no live workbook data and edits no source sheet.

All 40 tables enable RLS. Ordinary client roles, including `service_role`, have no direct application-table access. The server-only `impulso_backend` receives SELECT/INSERT only on service tables and narrow UPDATE columns in [access.sql](../../apps/supabase/schemas/access.sql). Posted amounts, kinds, currencies, accounts, dates, descriptions, request keys, original group membership, and frozen import snapshots remain unwritable to that role. Correction changes only void/version/actor/time metadata and inserts a replacement. DELETE, Finance files, Health, Auth secrets, and administration remain denied. Google sign-in alone creates no financial book or Health permission.

| [finance.assets](../../apps/supabase/schemas/finance/tables/assets.sql) | Manual nonledger asset identity, name, accepted ownership text, optional person and archive metadata. | Explicit owned assets remain distinct from investments already represented by accounts and from planned purchases. |
| [finance.asset_valuations](../../apps/supabase/schemas/finance/tables/asset_valuations.sql) | Nonnegative finite dated observation targeting exactly one account or manual asset, with source and retained replacement history. | [finance.import_batches](../../apps/supabase/schemas/finance/tables/import_batches.sql) | Actor/book-bound frozen workbook version, capture time, bounded manifest/reconciliation, reviewed SHA-256 digest, blockers and lifecycle. | Bounded protected preview/commit metadata; no URL fetching, formula execution or automatic source selection. |
| [finance.import_rows](../../apps/supabase/schemas/finance/tables/import_rows.sql) | Immutable source cell/period snapshots and accepted mappings, exact parsed values, roles, scoped result links, blockers, consumption and replacement history. | Stable active consumption is unique across requests and roles for workbook/sheet/cell/period in a destination book. Consumed rows require exactly one role-compatible result. |
| [finance.monthly_summaries](../../apps/supabase/schemas/finance/tables/monthly_summaries.sql) | Nonnegative accepted month/kind/category aggregate with an import-row provenance link and retained replacement history. | Month-level actual evidence creates no invented day, account, transaction or balance effect. |
| [finance.report_coverage](../../apps/supabase/schemas/finance/tables/report_coverage.sql) | One null-safe month/kind/category key selecting detail or summary, reviewed detail count/digest and expected version. | Explicit authority and changed-evidence checks prevent silent overlap; coverage never settles a bill or establishes account funds. |

Money uses `numeric(20,4)`. Native constraints enforce scope/currency, compatible category/transaction kinds, positive or nonnegative finite magnitudes as appropriate, supported calendar boundaries, one-target valuations, null-safe coverage keys, active component positions, occurrence identity, and unique active source consumption. Foreign-key and keyset/date paths are indexed. Unknown dates and facts remain null; a known valuation of zero is valid.

TypeScript validates raw decimal strings against the stored book precision before normalization, exact component sums, active scopes, self/null attribution, account-kind eligibility, expected versions, immutable history, allocation totals, freshness, accepted import mapping and digest, and live authorization after waits. Native constraints do not prove current permission, prevent all administrator rewrites, or calculate balances/payment state. Applications use the Edge Functions; administrator SQL remains more privileged. No custom SQL function or trigger supplies those business rules.

Reports read one bounded evidence snapshot and check every applicable person's current state, including budget/goal attribution and expected components. A budget comparison uses its own disclosed inclusive start/end dates and accepted person/category scope; month-only summaries cannot supply a partial-month or person-specific total, so unresolved usage and remaining allowance return null. Component excess never settles a different expected component: plans disclose actual allocated amounts, per-component remaining amounts and excess independently. Forecast effects respect the requested due-date horizon. Cash-flow completeness does not depend on an unrelated asset valuation or plan, and valuation-backed goals still require a supported account opening boundary.

## Private Auth projections: four views

These views are not additional application tables and do not duplicate managed Auth records. They are `postgres`-owned, use owner permission checks (`security_invoker = false`), and are inaccessible to ordinary clients. Explicit backend column grants provide a narrow bridge to managed Auth state.

| View and canonical definition | Projected columns | Granted backend use |
| --- | --- | --- |
| [private.auth_users](../../apps/supabase/schemas/private/views/auth_users.sql) | `id`, `updated_at` | Read `id`; timestamp-only UPDATE privilege permits locking the underlying account during onboarding. |
| [private.auth_sessions](../../apps/supabase/schemas/private/views/auth_sessions.sql) | `id`, `user_id`, `not_after`, `updated_at`, `oauth_client_id`, `scopes` | Read identifiers, expiry, client, and scopes; timestamp-only UPDATE privilege permits session row locks. |
| [private.oauth_clients](../../apps/supabase/schemas/private/views/oauth_clients.sql) | `id`, `deleted_at` | Verify that the OAuth client still exists and is not deleted. |
| [private.oauth_consents](../../apps/supabase/schemas/private/views/oauth_consents.sql) | `user_id`, `client_id`, `scopes`, `revoked_at` | Verify current consent and scope coverage for the user/client pair. |

The backend cannot select `updated_at` through these Auth projections merely because it holds UPDATE on that timestamp column. Password hashes, refresh tokens, and OAuth client secrets are not projected. Managed Auth and Storage schemas retain their Supabase-owned definitions.

## Responsibility boundaries

- Native primary/foreign keys, unique indexes, generated aliases, and row checks enforce structural integrity. Partial owner indexes guarantee **at most one** matching owner; they do not guarantee that an owner remains.
- Version columns start at one and must stay positive. Metadata and versions do not update automatically. Onboarding and supported Finance services enforce actors, metadata, active parents, permission, archives, purge guards, expected versions and atomic audit/receipts in TypeScript. Unimplemented Core/Health/file/sharing/purge lifecycles remain unavailable.
- Workspace membership, a verified self link, a basic-person grant, a financial-book grant, and a health-person grant are distinct. Onboarding creates the basic account scope; book creation explicitly adds its own owner grant. Membership alone never authorizes another book.
- File metadata constrains PDF/JPEG/PNG, positive size up to 20 MiB, and scoped paths. It does not provision a bucket or prove an uploaded object's content.
- The empty `api` schema is reserved for future explicit interfaces; current application operations run through TypeScript Edge Functions. There are no custom PostgreSQL functions, procedures, or application triggers in the current model.

See the [database workflow](../guides/database-workflow.md) for the ten reviewed migrations, [full-inventory assertions](../../apps/supabase/tests/database/impulso_schema.test.sql), and [planning/import native assertions](../../apps/supabase/tests/database/finance_planning_schema.test.sql). The five adaptation migrations are applied locally and the two database files passed 533 assertions on October 14, 2026 UTC; this result does not establish completed MCP integration, remote deployment or a live user import.

The later authorized [remote rollout](../guides/remote-deployment.md#finance-rollout-verification) independently verified all ten remote migrations, 40 RLS-enabled tables, zero custom application SQL routines and zero application triggers. Existing Core, receipt and audit counts and hashes were preserved; no user financial activity or live import was created.
